# FP-63 pre-commit review — 2026-10-20

Hold commit readiness for two P2 findings and fix the P3 estimate precision issue. This review changes no application source and performs no stage/commit/push/Jira/deployment action. It supersedes a no-gaps interpretation of the original passing implementation checks.

## Findings

1. **P2 — An open purchase confirmation adopts a refreshed target/revision without renewed review.** `fresh-price-front/src/features/user/shopping/ShoppingListsPage.tsx:59` sends `expectedRevision` from the latest list prop (`:33`), rather than the context when the purchase form opened. Its quantity/unit/amount/date remain in component state, while settings refresh automatically to new market/budget values (`:31`). Reproduction: open purchase at revision 2 for budget A/market A and fill quantity 1/amount 25; another session retargets the list to budget B/market B at revision 3; refresh the first page. The same composing confirmation remains enabled and submits revision 3 with the old entered values. Browser capture confirms that body and target; actual services accept it and create the expense against B/market B. The backend revision guard would reject the original revision, but the client has silently advanced it. The refreshed target is visible elsewhere in the page, so this is not a claim that no UI text changes; the defect is carrying an already-composing financial confirmation across that context change without invalidating or explicitly re-reviewing it. Capture the list/item/budget/market revision on form opening, or invalidate confirmation whenever its context changes and require a fresh review. Do not adopt the new revision as part of a refresh. Add real concurrent retarget/item-edit + refresh + confirmation regression coverage.
2. **P2 — Shared purchases link to personal expense history and hide the saved record.** `ShoppingListsPage.tsx:53` hardcodes `/user/budget/expenses` for every recorded purchase. `ExpenseListScreen.tsx:91–101` uses personal `scope=current` when scheduledBudgetId is absent, explicitly excluding shared expenses. Browser reproduction records a purchase against shared budget B and emits this unscoped href; real expense service queries return personal count 0 versus shared count 1 for the exact saved expense. The advertised history link therefore opens the wrong ledger and gives the user no route from that item to its saved shared entry. Derive history navigation from the item's immutable purchase-time expense/budget snapshot, not only the list's currently editable budgetLink, and include the URL-encoded scheduledBudgetId for shared spending. A later list retarget must not move existing purchase links to the new budget. Add personal/shared history navigation coverage, including retargeting after purchase and removed/deleted budget access.
3. **P3 — Binary floating-point multiplication misrounds valid centavo estimates.** `platform-backend/src/apps/freshprice/services/shoppingService.js:124` computes `Math.round(Number(row.price)*basis.quantity*100)`. A real fresh official quote `1.00` with a valid stored quantity `1.005000 kg` produces item and basket estimates of `1.00`, rather than the intended positive half-cent round-up to `1.01`. The multiplication becomes approximately 100.49999999999999 centavos before rounding. This affects estimates/remaining-after-estimate comparison, not the actual whole-PHP expense amount. Use exact scaled decimal/integer arithmetic for stored price, quantity and gram conversion, round once at the declared centavo boundary, and aggregate integer cents. Cover half-cent boundaries, g/kg equivalence and multi-item basket sums. An arbitrary epsilon does not establish correctness across the supported range.
