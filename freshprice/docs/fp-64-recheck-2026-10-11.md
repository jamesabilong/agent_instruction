## Confirmed gaps

1. **P2 — Old-session budget saves resolve after switching accounts during hydration.** `fresh-price-front/src/store/budgetStore.ts:109` awaits hydration after its last generation check. If account A's write succeeds, hydration remains pending, and the user changes to account B, the old save still resolves. `ExpenseInputScreen.tsx` subsequently submits overridden prices, sets shared budget preferences, and navigates. The price submission uses the current authentication state, so this timing window can attribute that follow-up write to B. Add a generation check after hydration and cover this interval with a regression; preserve the server write already committed for A.

   Fresh reproduction: mock successful `createExpense`, delay `fetchBudget`, start `addExpense`, wait until hydration starts, switch token/user, then release hydration. The expected session-change rejection fails with `promise resolved "undefined" instead of rejecting`. The temporary test was removed after execution.

2. **P2 — Deployment drops the persisted maintenance setting.** `.github/workflows/deploy.yml:125-129` exports selected VPS `.env` keys but omits `FRESHPRICE_MAINTENANCE`, which `docker-compose.prod.yml:91` reads from the process environment. Frontend/Sugilanon dispatches can therefore reset maintenance to false despite an enabled setting in `.env`. Export the flag and test both values through stack rendering.

   Fresh reproduction: copy production Compose to a temporary directory, write a synthetic `.env` containing `FRESHPRICE_MAINTENANCE=true`, extract the workflow's actual key list and export those synthetic values, then run `docker stack config`. The frontend renders `FRESHPRICE_MAINTENANCE: "false"`. This client-side check requires no Docker daemon, production access, or real credentials. Temporary files were removed.
