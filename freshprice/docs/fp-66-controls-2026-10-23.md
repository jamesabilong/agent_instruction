## Exemption policy

- `AUTH_TEST_EXEMPTIONS_ENABLED` defaults to false. All existing login/auth flows remain compatible before migration or activation; disabled login skipping performs no exemption-table query.
- Own account means the authenticated administrator's own account ID. There is no separate test-account ownership/delegation model and no ability to select another user's account. Both management and enforcement recheck the current database role rather than relying solely on JWT role claims.
- One persistent rule per account. Creator/target are the same user ID. Exact canonical IPv4/IPv6 only; no wildcards, chains, CIDRs, private/gateway/loopback/link-local identities. Default duration 60 minutes, server-bounded to 1–240 minutes. Creation/replacement/revocation requires a fresh current password in that request, plus a verified public caller identity. Passwords/proofs are never stored in the UI or database. A separate non-exempt reauthentication quota applies (10 changes/attempts per IP/15 minutes in production; 100 in development/test).
- Explicit current-IP selection or exact manual address replacement; no automatic IP enrollment from login attempts. A rule affects only POST login throttling. Password checking, sessions/roles, global API limiting, registration and password-reset protection remain enforced. The admin UI explains shared-NAT limitations.
- User-row then rule-row locks serialize creation, replacement, revocation and enforcement. Expected revision 0 creates the first rule; replacements/revocations require the current revision and stale writes return 409. Enforcement reads the database on every request, with no process-local exemption cache. In-flight decisions linearize at the locked check; revocation affects subsequent checks.
- Expiry applies immediately at the time boundary without cleanup jobs. An expiry audit is recorded lazily on the next rule read/check. Creation, replacement, use (including attempts later rejected by password validation), expiry, revocation and operator revocation have transactionally persisted allowlisted audit fields; audit failure falls back to normal login throttling.
- One rule row is reused on replacement, preserving audit history. The admin page shows current lifecycle state and the latest 100 own-account events. Retain the audit table according to operator policy; no automatic destructive retention job is introduced.

## API and UI

Shared endpoint `/api/platform/auth/testing-exemption`:

- GET returns enabled/verified/current-IP/account, rule state and latest 100 audit events. Requires authenticated current admin; no-store.
- PUT accepts `currentPassword`, `revision`, `reason`, optional `durationMinutes` (default 60) and either exact `ip` or explicit `useCurrentIp: true`. Returns the persisted rule. Requires current admin, fresh password, enabled feature and trusted public caller identity.
- POST `/revoke` accepts `currentPassword` and `revision`, with the same guards.

FreshPrice `/admin/authentication-testing` is guarded by normal admin routing and linked in the sidebar. Typed APIs use the centralized client; errors are visible, stale writes require refresh, passwords clear after every submission, state remounts on account changes, and controls are disabled when the feature or identity is unavailable. ## Recovery and rollout

Normal recovery is the existing 15-minute login cooldown and existing password-reset process (production mail delivery still requires an available configured/operator process). Authenticated controls cannot recover a logged-out or already-throttled administrator. Invalid credentials remain invalid. There is no public recovery endpoint or role/password override.

For a compromised/misconfigured rule, an operator must first obtain explicit authorization, record identity/reason in protected operational records, and run `node src/scripts/revoke-auth-test-exemption.js <username> <non-secret reason>` in the authorized backend context. It only revokes the rule, increments revision and writes `operator-revoked` audit. It never clears limiter buckets, changes roles/passwords or creates an exemption. Wait for normal cooldown afterwards. Do not put passwords, tokens or keys in the command/reason. Emergency global disabling uses the separately authorized targeted backend environment update; retain operational evidence outside Git.
