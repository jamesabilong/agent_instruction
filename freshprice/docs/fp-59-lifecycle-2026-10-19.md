## Ownership transfer

Only the current owner may propose another accepted member, including a viewer. The recipient must explicitly accept within seven days, and may decline; the current owner may cancel. The original owner retains ownership until acceptance. One pending proposal is enforced by a partial unique index. Repeating the same live recipient/membership request returns that proposal; proposing someone else cancels the previous request.

Acceptance locks the scheduled parent and rechecks current ownership, pending status, expiry, and the exact accepted membership UUID. Removal/re-invitation, stale tabs, superseded IDs and simultaneous proposals cannot create another owner. Same successful outcome retries return the existing result without repeating a transfer. Acceptance updates the budget owner, removes the new owner's redundant membership, and adds the previous owner as an accepted contributor in one transaction with activity/notifications. Existing expense authors remain unchanged; ownership alone does not grant rights to edit another author's expense.

The budget screen shows request/accept/decline/cancel controls and refreshes server state after writes using the existing session-generation guarded store. Transfer reads discard late responses on account switches. Background hydration preserves the selected recipient; changing account or budget clears it. Another session's owner controls become current after refresh, while every backend management write immediately rechecks the owner.

## Monthly recurrence policy

- A template snapshots the source's name, amount, note, original start/end dates and allocations. Later source edits do not change the snapshot. A creator can have one active/paused template per source; cancellation permits creating a new snapshot with a new UUID.
- Templates belong independently to their creator. Source transfer/deletion does not transfer or delete future scheduling. This is explained before creation and transfer. Generated instances can themselves be shared/transferred, but cannot be turned into another template.
- Each original date shifts independently by calendar months. January 31 becomes February 28/29, then March 31; a January 31–February 2 window becomes February 28–March 2. Calculations use server Asia/Manila business dates, with date-only fields rather than client timezone arithmetic.
- First occurrence is at least one month after the source start. Creation skips starts before today. Each instance receives independent allocation IDs, no expenses and no memberships; it is private to the template creator. No financial history or household access is silently copied.
- Active templates catch up due periods after downtime, up to 24 periods per transaction. Pause blocks generation. Resume skips starts missed while paused, preserving today as eligible. Cancel permanently stops generation while retaining existing instances and the template record. An old creation UUID returns its cancelled snapshot rather than restarting it.
- Backend startup and hourly sweeps page through all due templates in stable ID order, 50 at a time. Each ID is attempted once per sweep; errors are reported after later pages are processed. A template row lock and unique template/occurrence index deduplicate overlapping workers/manual retries. New instance IDs are random UUIDs, so another account cannot preclaim predictable future IDs. Existing generated IDs remain valid. Instance creation, allocations, activity and cursor advance commit atomically. Soft-deleted instances are detected with paranoid=false and never recreated.
- Creator-only manual generation is also available. The API takes no simulated date. Template lists, errors, retries and pause/resume/cancel confirmation appear above scheduled budgets. Read responses are discarded after account switches, and lifecycle writes reuse the existing guarded write/hydration path.
