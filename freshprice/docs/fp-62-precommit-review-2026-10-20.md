## Findings

1. **P2 — Collapsing the panel discards the composing translation.** `fresh-price-front/src/features/wiki/EnrichmentPanel.tsx:72–76` places the stateful editor inside `open && ...`. Closing the native details panel unmounts the editor, discarding its summary, provenance, months, consent and other local form state. Reopening initializes an empty form without a discard warning. This is especially problematic when collapsing notes to compare the canonical source. Actual Chromium/React reproduction filled summary, source URL and geography, closed and reopened the disclosure, and observed all three become empty. Keep the editor/form state mounted across disclosure toggles (native details can hide it), or retain an account/product-scoped composing draft above that conditional; preserve existing account-switch clearing. Add collapse/reopen and collapse-during-submit coverage.
2. **P2 — Approved enrichments cannot be independently retracted.** `platform-backend/src/apps/freshprice/services/wikiEnrichmentService.js:68–80` accepts only approve/reject and rejects every already-reviewed entry. The UI exposes review actions only for pending rows (`EnrichmentPanel.tsx:55`); the only withdrawal endpoint changes recognition, not content. After approval, an editor who finds an erroneous translation or unsupported regional claim cannot unpublish that variant while keeping the canonical wiki and other valid variants available. Real migrated PostgreSQL/service reproduction approves an entry, attempts rejection, receives 409 “This proposal was already reviewed”, and confirms the entry is still returned publicly. Treat this as a missing moderation lifecycle transition, not a claim that the existing pending-proposal rejection route promised to retract content. Add an explicit operator retraction/unpublish action with history and appropriate concurrency checks; cover removal from both public enrichment and seasonal queries without hiding unrelated content. Author cancellation of obsolete pending proposals is a related workflow gap, separate from the deliberately name-only recognition endpoint.
3. **P3 — Proposal retries have no stable operation identity.** `wikiEnrichmentService.js:44–50` generates a new UUID for every invocation; `EnrichmentPanel.tsx:27–28` preserves the form after a failed response but sends no stable request key. Repeating identical submission data against the real services created two different pending rows. This models the retry after a committed response is lost; the DB probe does not itself inject an HTTP transport failure. Duplicate pending proposals can consume rate limits and be reviewed/published separately. Add a client-generated submission identity retained through uncertain retries, server-side payload/account validation and atomic deduplication; a deliberate new proposal should receive a new identity. Add a real committed/lost-response retry case.
