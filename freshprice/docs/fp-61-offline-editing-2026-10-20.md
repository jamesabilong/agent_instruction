# FP-61 — Durable offline expense editing (2026-10-20)

Local implementation on matching frontend/backend `FP-61` branches, based on published FP-60 heads. Includes the FP-59 monthly calendar clamp follow-up; FP-59/FP-60 are still upstream release dependencies. No staging or production readiness is implied.

## User behavior and policy

Saving an expense create/edit first persists an account-scoped IndexedDB draft. Only transaction completion acknowledges local durability. The sync center shows queued, syncing, synced, failed and conflict states, separate pending creation amounts, server confirmations, retry and discard. Confirmed totals continue to come exclusively from the API; pending edits do not replace displayed confirmed amounts.

Foreground sync runs on mount, focus, reconnect and a ten-second interval, with bounded exponential transport retry delays. Unrelated drafts continue after permanent failures. Each expense permits one unresolved edit, preserving entity order. Creates use temporary UUID identities; server-generated IDs arrive in confirmations. IndexedDB claims and expiring tab leases coordinate replay; durable server receipts provide correctness even if a lease expires while a request is in flight. Draft payloads contain only whitelisted expense fields, never bearer tokens.

A loaded form may save while offline. After restarting offline, the production PWA restores the app and sync center from the shell cache, with existing pending drafts. Creating further drafts against unloaded budget/catalogue data requires reconnecting first; the queue is not an offline copy of private server data. Membership, ownership, invitations, deletion and settlement confirmation remain online-only.

Explicit logout/account change synchronously rotates a durable account draft-generation marker before clearing identity, clears local visibility, and purges obsolete records asynchronously. Replay and completion check the marker, so tab closure or blocked IndexedDB cleanup cannot resurrect discarded work. Later refresh resumes physical cleanup; new drafts from the same account use the new generation. Legacy drafts without a generation remain valid until that account is discarded. If the marker cannot be persisted, the logout/account-switch action fails before clearing identity. Storage events synchronize auth identity across tabs; receipt requests also carry `draftAccountId` so a changed cookie cannot submit an old account's expense under a new account. A queue replay 401 retains the draft and requires same-account reauthentication/retry. Expiry from unrelated requests clears authentication and hides drafts while retaining their account marker; same-account sign-in restores failed drafts for explicit retry. Signing into a different account or explicit logout purges the previous account’s drafts.

A revision conflict retains both the submitted draft and returned server expense. Applying the draft requires explicit review/confirmation and creates a new mutation key at that reviewed revision. The confirmation passes the exact displayed revision and compares it with the stored conflict transactionally; a conflict refreshed in another tab requires a new review. A second server change conflicts again. Invalid permissions/deleted entities retain failed drafts for retry/discard. Current-budget identity is captured and checked so deleting/replacing/disabling a current budget cannot silently redirect a draft. Tracked split changes retain FP-60 correction restrictions.

Quota/storage failures reject saving and keep form input; the app does not claim durability. Browsers without IndexedDB retain confirmed-online behavior and reject offline saves. Unknown/newer IndexedDB versions fail closed without deleting stored records; close older tabs before upgrades. Version 1 creates an additive `drafts` store. Future upgrades must migrate existing drafts in the version-change transaction and retain pending keys/payloads. If disposal itself fails, the UI directs the user to clear site data before sharing the device.

## API and persistence

Existing POST `/api/freshprice/user/expenses` and PUT `/api/freshprice/user/expenses/:id` accept optional `mutationId` (UUID), `draftAccountId`, and `expectedBudgetId` (current-budget UUID). Mutation PUT additionally requires `expectedRevision`. Legacy callers retain their existing contracts.

`20261020000001-expense-mutation-receipts.cjs` adds `expense_mutations`: UUID mutation key, authenticated actor, SHA-256 signature of the normalized writable payload/operation/expense/revision/budget identity, expense identity and original JSON response. Receipt creation and the expense write share one transaction under the existing actor/parent locks. Authorization and target validation run again on every replay. Same key/values returns the original receipt without another update/revision/activity; changed values return 409 `MUTATION_KEY_REUSED`. Missing previously committed expenses return 410 `EXPENSE_DELETED`; receipts survive expense deletion. Revision mismatches return 409 `REVISION_CONFLICT` with the current expense. Changed current budgets return 409 `BUDGET_CHANGED`; account mismatch returns 403 `DRAFT_ACCOUNT_CHANGED` before service execution. No server deletion can cause replay to create another expense using an existing mutation key.

## Release and rollback

Deploy the additive migration/backend before the frontend. Keep receipts throughout rollback and do not replay pending drafts against a backend without this contract. Migration down is allowed only while receipts are empty; nonempty rollback is intentionally blocked. PWA shell upgrades must retain IndexedDB; service-worker/cache recovery does not clear the queue. No background sync is required.

Rehearse against restored staging data: account expiry/reauthentication, permission revocation, deleted budgets, uncertain transport outcomes, concurrent devices/tabs, production offline restart and update from a previous app version. Verify deployment proxy/cache headers and actual-device storage eviction behavior separately. Local-only fixtures/specs/reports under `testing/tickets/FP-61` must be backed up outside app commits.
