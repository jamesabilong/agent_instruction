# FP-43 post-commit audit — 2026-10-02

Scope: frontend `1b3893fe`, backend `4ea8dc3`, deployment `3b8261a`. The original audit made no application changes; the subsequent resolution is recorded below.

## Resolution — 2026-10-02

All four findings are fixed locally. Shared modal and budget tutorial dialogs suspend portal visibility and focus management during recovery while preserving mounted editor inputs. Route/session resets release old probe/recovery ownership; promise cleanup checks identity before clearing current work. Optional layout market loading explicitly bypasses global outage handling. nginx uses a higher-priority `/assets/` prefix so hashed assets retain immutable caching.

Validation: frontend lint/build, 240 unit tests, 17 development Chromium flows, one production/service-worker Chromium flow, and nginx/Caddy HTTP checks all pass. Regressions cover modal input preservation and write non-replay, stale promise ownership, broken user links during API downtime, and hashed-asset cache headers. Changes are uncommitted and undeployed; actual VPS/staging release gates remain.

## Original confirmed findings

1. **P1 — Open dialog can block recovery.** `AvailabilityBoundary` hides/inerts only its normal child wrapper. The shared Headless UI Modal renders its dialog through a body portal, outside that wrapper. When outage state activates while a dialog is open, the dialog remains visible and its focus/inert management makes the new recovery heading inaccessible. Users saving through a dialog can be unable to reach Try again. Reproduced with the actual shared Modal and AvailabilityBoundary: the dialog remains visible, the recovery text exists, but the recovery heading is absent from the accessible roles. Fix by coordinating portal visibility and focus trapping with outage state while preserving editor input. Add a real modal-save failure/recovery regression.

2. **P2 — Recovery promises survive a route/session reset.** `resetAvailability` clears queued reads and UI state but leaves the module-level `recovery` and `probe` promises active. Starting recovery for a new page returns the previous recovery promise before setting the checking state. Reproduced with an unresolved old-page read: after reset and a new queued read, Try again returns the old promise, never calls the new read, and leaves checking false. Fix with generation-scoped probe/recovery ownership and identity-safe cleanup; test a route/session change during an in-flight retry. The existing token checks prevented old reads from being replayed in the tested cases, so this finding concerns retry blocking rather than demonstrated account-data leakage.

3. **P2 — Optional layout request replaces missing-page UI.** The user layout's UserContextProvider fetches markets on every mount and deliberately treats failure as optional. The client exempts only notification requests from global outage handling. With API/readiness unavailable, opening an unknown user URL turns its not-found screen into the global outage screen because the market lookup fails. Reproduced with the actual provider, client interceptor and boundary. Fix by explicitly marking optional/background calls, or separating route-critical availability from layout lookups. Cover broken user links during API downtime and optional layout failures on pages that do not need markets.

4. **P3 — Versioned asset caching is shadowed.** The new extension regex in nginx.prod.conf precedes the `/assets/` regex. For hashed JavaScript/CSS, it matches first and returns `Cache-Control: no-cache`, preventing the existing immutable-cache rule from running. Confirmed against isolated nginx: `/assets/index-D_r5ZuQF.js` returned 200 with no-cache. Fix by making `/assets/` an explicit higher-priority prefix or ordering its regex first; retain genuine 404 responses for missing assets and add a cache-header assertion.
